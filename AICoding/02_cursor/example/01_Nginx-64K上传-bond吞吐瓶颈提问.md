# Nginx 64K 上传转发：bond1 吞吐瓶颈分析

## 1. 目标与验收

**目标**：分析 172.31.16.99 上 Nginx 做 HTTP 转发时，bond1 吞吐约 17.8GB/s 打不满的原因，并给出可落地的优化建议。

**验收标准**：
- 结论必须分层（网卡/软中断/跨 NUMA/Nginx worker/后端…），不能只给泛泛建议
- 每个关键判断附：采集命令 + 关键数字
- 优化建议按「预期收益 / 风险 / 是否需停测」排序
- 不确定处明确标注，不要把假设写成事实

## 2. 约束（必须遵守）

- 登录路径：先免密 root 登录跳板机 `10.142.80.17`，再免密登录目标机
- 可登录机器：`172.31.16.99`（Nginx 网关）、`172.31.16.95/96/97`（后端）
- **只读采集**：禁止修改任何参数、配置、服务、IRQ、sysctl；禁止重启
- 压测仍在进行：采集要轻量、可重复，避免干扰测试

## 3. 拓扑与角色

```text
5 × Client (200Gb bond)
        │
        ▼
   Nginx  (172.31.16.99)
   VIP(172.31.16.120)
   bond1 = eth20 + eth21
        │
        ▼
3 × Nginx
172.31.16.95
172.31.16.96
172.31.16.97
```
- 客户端 → VIP 172.31.16.120 发 HTTP 请求（body=64K）
- .99 上 Nginx 转发到 .95/.96/.97
- 后端收到 body 后直接 discard，返回 200 OK

## 4. 机器与当前生效配置（事实）

### 4.1 网关机 172.31.16.99
```bash
Intel Xeon Gold 6384 @ 2.6GHz
2 Sockets / 112 vCPU / 251GB

NUMA0 (Socket0): CPU 0-27 + HT 56-83；L3 42MB；RAM ~128GB
NUMA1 (Socket1): CPU 28-55 + HT 84-111；L3 42MB；RAM ~129GB

eth20: 100Gb, 63 queues，在 NUMA0
eth21: 100Gb, 63 queues，在 NUMA0
bond1 = eth20 + eth21 = 200Gb
```

### 4.2 当前 OS/网卡参数（已生效）
- 软中断/IRQ：eth20 绑 CPU 0-13；eth21 绑 CPU 14-27
- 中断合并：eth20/eth21 均为 rx-usecs=256，rx-frames=256

## 5. 测试方法与当前现象

- 压测：5 客户端同时打 VIP，body=64K 上传

- 当前观察：bond1 吞吐约 17.8GB/s（相对 200Gb 理论能力明显偏低）
