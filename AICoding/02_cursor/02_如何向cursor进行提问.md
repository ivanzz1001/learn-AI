# 我应该如何科学的使用cursor Agent进行提问？

下面结合 我这些天进行的 Nginx 压测排查场景，用 Cursor Agent 提问可以按下面这套「科学」方式做。

## 1. 核心公式

目标 + 边界 + 必要上下文 + 验收标准

| 要素       | 作用                  | 你的例子                                        |
|:----------|:----------------------|:-----------------------------------------------|
|**目标**    |Agent要产出什么         | 找出 bond1 卡在 ~17.8GB/s 的原因 + 优化建议        |
|**边界**    |不能做什么               |只读采集，禁止改目标机参数                          |
|**上下文**  | 拓扑、机型、已配参数、现象 |VIP、NUMA、irq 绑定、rx-usecs、测试方法            |
|**验收**    |怎样算完成               |给出瓶颈层级（网卡/软中断/Nginx/后端）+ 可验证的下一步 |

少写「帮我看看」，多写「结论要落到哪一层、依据是什么」。

## 2. 提问习惯（按优先级）

1. **一事一聊**
   
   压测排查、改文档、写脚本分开开新对话。长线程会压缩旧上下文，结论会漂。

1. **只 @ 相关材料**

   @相关描述/...md、@拓扑说明 够用就行；不要一次塞十几个文件。不确定文件时，让 Agent 自己搜，或先用 Plan。

1. **复杂事先 Plan**

   「先列采集清单和假设，等我确认再 ssh 拉数据」——比直接让它满机器扫更稳。

1. **写清权限与操作边界**

   你已经写对了：跳板机 → 目标机、root 免密、禁止修改。这类运维任务，边界比技术细节更重要。

1. **要求可验证输出**

   例如：「每个结论对应一条命令输出；区分相关 vs 因果；优化建议按收益/风险排序」。

1. **跑偏就停、改提示、必要时新开**

   比在错误方向上继续追问更省时间。

## 3. 针对你这类排查的推荐模板

【目标】分析 172.31.16.99 上 Nginx 64K 上传转发时 bond1≈17.8GB/s 的瓶颈，并给优化建议。

【现象】5 客户端 → VIP → 3 后端 discard；当前吞吐 X；CPU/软中断大致表现（如有）。

【环境】拓扑、NUMA、irq 绑定、中断合并、Nginx 关键要点（@相关结果文档）。

【约束】
- 经跳板机 10.142.80.17 登录采集
- 只读，禁止改任何参数/重启服务
- 测试仍在跑，采集要轻量、可重复
  
【请按此流程】
1. 先列出假设与采集清单（等我确认或直接执行轻量采集）
2. 用数据验证/排除假设
3. 结论：瓶颈在哪一层（网卡/IRQ/Nginx worker/跨 NUMA/后端…）
4. 优化建议：改什么、预期收益、风险、是否需停测
   
【验收】每个关键判断附命令与关键数字；不确定处标明。

你附件里的拓扑和约束已经很好；再补两点会更稳：当前观测指标（CPU%、softirq、rx drop、Nginx worker 数）和期望输出结构。

## 4. 模式怎么选
- Ask：只解释、不改文件、不连机器时用。
- Agent：要 ssh 采集、读仓库结果、写分析文档时用。
- Plan：范围大、假设多、怕乱动时先 Plan。
  
## 5. 常见反模式
- 「帮我优化一下」——没有目标吞吐、没有禁改边界。

- 同一对话里混「分析原因」和「帮我改 nginx.conf」——上下文互相干扰。

- 堆满无关历史报告——关键信号被淹没。
  
- 不写验收——Agent 容易给泛泛建议，无法对照数据。
  
一句话：把 Agent 当会执行的同事——给清目标、禁区、材料和「怎样算做完」；复杂事先对齐计划，简单事直接给具体验收。你这份压测提问已经接近优秀模板，补上「当前指标 + 输出结构」即可。

## 7. 背景描述复杂，如何提问？

比如我有一个提问，需要的背景描述很多，需要放到一个文件中，那我如何在文件中描述清楚，并告诉Agent呢？

**做法是**：背景写进文件，对话里只发「任务指令 + @文件」。文件负责稳定上下文，聊天负责本轮要做什么。

### 7.1 怎么告诉 Agent
在输入框里：
```text
请按 @打不满网卡/LVS(FNAT)模式CPU打不满提问.md 执行排查。
本轮重点：先做只读采集，确认 softirq / rx_discards / IPVS 哪一层先打满。
```
要点：
- 用 @路径 把文件挂进上下文（比「去读 xxx」更稳）。
- 聊天里写本轮任务；文件里写可复用背景。
- 背景更新了就改文件，新开对话再 @，不要靠长线程记旧设定。

### 7.2 文件怎么写才「清楚」

按固定章节写，Agent 和你自己都更好扫。建议结构：

```text
# 任务标题（一句话目标）

## 1. 目标与验收
- 要回答什么 / 交付什么
- 怎样算完成（例如：瓶颈分层 + 每条结论有命令依据）

## 2. 约束（先写，很重要）
- 只读 / 禁改 / 登录路径
- 测试仍在跑时的采集限制

## 3. 拓扑与角色
- 谁连谁、VIP、角色（ASCII 图即可）

## 4. 机器与已定配置（事实，不是猜测）
- CPU/NUMA、网卡、irq、已调参数
- 只保留「当前生效」的配置；过程实验放到「已尝试」

## 5. 测试方法与现象
- 客户端数、body 大小、压测方式
- 当前数字（吞吐、CPU%、drop…）
- 和对比基线的差距（若有）

## 6. 已尝试与结果（避免 Agent 重复建议）
- 做过什么 → 结果如何（一行一条）

## 7. 相关材料（可选）
- @其它结果文档路径，或写相对路径列表

## 8. 建议工作流（可选）
1. 列假设与采集清单
2. 采集验证
3. 结论 + 优化建议（按收益/风险）
```

### 7.3 文件 vs 聊天：怎么分

|放进文件     |	放进本次聊天                     |
|:-----------|:--------------------------------|
|拓扑、机型、长期配置 |本轮具体问题（「先查 discards」）|
|登录与禁改规则      |临时补充（「现在吞吐掉到 15GB」） |
|历史调优与踩坑      |输出格式偏好（「写进某某 md」）   |
|稳定基线数字        |「只分析、先别 ssh」这类本轮开关 |

原则：文件 = 说明书；聊天 = 工单。

### 7.4 写法上的几个技巧

1. **事实与假设分开**

   「rx_discards 在涨」是事实；「所以是中断合并太猛」是假设，标清楚。

1. **大段命令输出可折叠或外链**

   必要结论写在正文；完整 ethtool/sar 放「附录」或另文件 @，避免主文件淹没目标。

1. **数字带单位和采集时刻**

   bond1 ≈ 17.8 GB/s（2026-08-14 压测中） 比「大概十八」有用。

1. **对比组写清**

   「DR 20.9GB vs FNAT 20GB」这种基线，单独一小节。

1. **约束置顶**

   「禁改目标机」放最前，减少 Agent 先提 sysctl -w。

### 7.5 最小可用对话示例
```text
@打不满网卡/xxx提问.md
按文件中的目标与约束执行。
先不要给泛泛优化清单：先采集验证文件里的现象，再下结论。
交付：瓶颈层级 + 依据命令 + 按优先级的建议（标明是否需停测才能改）。
```
一句话：背景文件用固定章节写清目标/约束/事实/已尝试；对话里 @文件 + 写清本轮要做什么。
